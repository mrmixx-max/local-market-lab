# v1.0 Roadmap — priorisiert

**Stand:** 2026-08-24, nach Stable-Release v0.9.1
**P0 ist leer:** keine reproduzierten Bugs, keine Sicherheitsprobleme, keine
falschen Metriken, keine beschädigten Exporte zum Release-Zeitpunkt.

Jedes Feature dokumentiert: Problem / Nutzerwert / Module / API-Auswirkungen /
Datenmodell / Teststrategie / Sicherheits-/Performance-Risiken / Aufwand /
Abnahmekriterien / Breaking Changes.

## P1 — Verlässlichkeit & Betrieb

### 1.1 Job-Queue für lange Berechnungen
- **Problem:** Monte Carlo >5k Runs, Tuning und große Backtests blockieren
  API-Request und UI für die gesamte Laufzeit.
- **Nutzerwert:** UI bleibt responsiv; Fortschritt sichtbar; Jobs abbruchbar.
- **Module:** neu `packages/jobs/` (Queue, Worker, Status-Store);
  `apps/api/main.py`; Desktop-App (Polling/WebSocket).
- **API:** neue Endpunkte `POST /jobs`, `GET /jobs/{id}`, `DELETE /jobs/{id}`;
  bestehende synchrone Endpunkte bleiben (Deprecation später).
- **Datenmodell:** Tabelle `jobs(id, kind, params_json, status, progress,
  result_ref, created_at, finished_at)`.
- **Tests:** Unit (State-Machine), Integration (Submit→Progress→Result,
  Abbruch mitten im Lauf), Lasttest mit 10 parallelen Jobs.
- **Sicherheit:** Job-Parameter strikt validieren (keine Pfad-/Command-Injection
  über params); Ergebnis-Zugriff auf eigenen Workspace beschränken.
- **Performance-Risiko:** Worker-Pool-Konkurrenz um SQLite → WAL-Modus +
  Read-Pool prüfen.
- **Aufwand:** M–L (~1–2 Wochen).
- **Abnahme:** 10k-Run-Monte-Carlo asynchron; API antwortet <100 ms währenddessen;
  Abbruch terminiert den Worker sauber.
- **Breaking Changes:** keine ( additive Endpunkte).

### 1.2 Mindestordergrößen & realistisches Rebalancing ✅ IMPLEMENTIERT
- **Problem:** Vorschläge ignorieren Stückelung/Mindestgrößen → praktisch teils
  unausführbar.
- **Nutzerwert:** direkt umsetzbare Vorschläge; weniger Fehlkäufe.
- **Module:** `packages/portfolio/rebalancing.py`.
- **API:** neuer optionaler Parameter `min_order_value`, `lot_sizes` je Symbol.
- **Datenmodell:** Portfolio-Config um Ordergrenzen erweitert (optional, Default
  unverändert).
- **Tests:** Property-Tests (Vorschlag ≥ Mindestwert oder verworfen), Summen-
  Erhalt, Cash-Restbestand ≥ 0.
- **Sicherheit:** weiterhin nur Vorschläge, kein Ausführungspfad.
- **Aufwand:** S–M (~2–4 Tage).
- **Abnahme:** Beispielportfolio mit 50 €-Mindestorder erzeugt nur ausführbare
  Vorschläge.
- **Breaking Changes:** keine.

### 1.3 Fortschritts- & Abbruchanzeigen (Desktop + CLI)
- **Problem:** Lange Läufe ohne Feedback; Abbruch nur via Prozess-Kill.
- **Nutzerwert:** Kontrolle und Transparenz.
- **Module:** Desktop-App (Progress-Bindung an Job-API), CLI (`--progress`).
- **Aufwand:** M (~3–5 Tage, gemeinsam mit 1.1).
- **Abnahme:** Fortschrittsbalken bei MC ≥1k Runs; Ctrl+C bricht sauber ab.

### 1.4 Modell- & Datenversionsverwaltung
- **Problem:** Modellversion/Data-Hash sind in Resultaten vorhanden, aber kein
  durchgängiges Registry.
- **Nutzerwert:** Jede Analyse beliebig später exakt rekonstruierbar.
- **Module:** `packages/artifacts/manifest.py` ausbauen; Storage-Schema um
  `model_registry` erweitern.
- **Tests:** Round-Trip (Run → Manifest → Re-Run identisch), Migrationstests.
- **Aufwand:** M (~1 Woche).
- **Abnahme:** Alter Run per ID erneut ausgeführt → byte-identisches Ergebnis.

### 1.5 Streaming/WebSocket-Architektur
- **Problem:** `/ws/market` liefert simulierten Feed.
- **Nutzerwert:** Echte Kursupdates ODER ehrliches "nicht verfügbar".
- **Module:** `apps/api/ws.py`; Adapter-Layer.
- **Entscheidung vorab:** Entweder echte Provider-Anbindung (Lizenz/Ratelimits
  prüfen) oder Feature explizit entfernen. Kein simulierter Feed in v1.0.
- **Sicherheit:** Rate-Limits, Backpressure, Auth am WS-Endpunkt.
- **Aufwand:** M–L (je nach Variante).
